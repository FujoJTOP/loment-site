LibL

Loment 的标准库，做成 C 的形状：与 libc 相同的函数名、相同的参数序、相同的 返回值 —— 给已经懂 C 的人用。一个库有两面，不是两个库。

尚不可用

这个库已经写好，代码在主分支上。它不在任何发布里 —— 正在切出的这一版的发布说明把它和 libc 一起列为不可用 —— 所以这一页上的任何东西都不是 你今天能用的。

它为什么还在这站上。因为它是某个语言一直悬着的问题的第一份答案：标准库 对于一个从 C 走过来的人是什么样子。"写好"不等于"准备好了"，而在这里两者差得足够远， 只说前者会误导人。

为什么要有第二面

标准库本来就在，而它一个 libc 名字都没有 —— 没有 strlen， 没有 printf，没有 malloc。那不是一处遗漏，而是一种形状。它的 函数取一个显式的长度，而不是去找结尾符；用一个偏移量寻址进缓冲区；而且从不接受可变数目 的参数。这门语言里没有以 NUL 结尾的字符串，也没有变参函数，所以那个库是照着语言的样子 写成的。

那个形状对写 Loment 的人来说是对的，而对懂 C 的人来说是一道墙。第二面回答的是另一个 问题：要是你从没听说过 Loment，这会叫什么？strcmp，它返回 的东西和 C 的一样。qsort。isdigit。没有东西要学。

两面指向同一批字节。isdigit 调用的是库自己的字符判定； memcpy 调用的是它自己的拷贝例程。所以两面本来会带来的那种失败 —— 同一个字节 因为你问的是哪个名字而给出不同的回答 —— 是结构上不可能，而不只是被避开了。

两种入口

LibL 是这个库的名字；std 仍然是这个包的名字。两个入口都到达 同一个包，区别在于它们各自带进来多少东西。

use std

整个包。LibL 之前写下的一切都已经这么做，而且它继续可用。代价是：一个包级入口把每个 模块拉进一个单元，而这门语言的发射符号空间是平的 —— 于是那些顶层名字必须 彼此唯一，编译时间的增长也快过模块数。

use libl

那四个 libc 面和它们所依赖的东西 —— 六个模块。一个小面：编译得快，而且几乎没有东西会 和它撞名。当你想要的只是 libc 名字时，就用这个入口。

它覆盖什么

一个 libc 头对应一个模块，而这个映射本身就是遵循 libc 的一部分。

<string.h>

strlen、strcpy、strncpy、strcat、 strcmp、strncmp、strchr、strrchr、 strstr、strspn、strcspn、strpbrk、 strtok_r、memchr、memcmp、memcpy、 memmove、memset。

<ctype.h>

isdigit、isalpha、isalnum、 isspace、isupper、islower、 isxdigit、ispunct、isprint，以及这一组里 其余的，外加 toupper 和 tolower。

<stdlib.h>

不需要堆就能构建的那一半：atoi、atol、strtol、 strtoul、abs、labs、llabs、 qsort、bsearch。

<stdio.h>

只有格式化那一半：snprintf 和 sprintf。这个发布里没有 FILE，原因在下面。

再加上一个 libc 没有的函数，而它才是有意思的那个 —— 见下。

对照物就是 libc 本身

标准库其它每一个部分，都是把 Loment 算出的东西和 Python 算出的东西比对来判的。 对这个问题来说那是错的对照物，而且可证：恰恰在定义"行为像 libc"的那些边界上 —— strncpy 会不会补零、strcmp 返回的是一个符号还是一个差、 strchr 会不会找到结尾符、memmove 在区间重叠时是否安全 —— Python 和 libc 给出的不是同一个答案。拿 Python 当对照，会让两份实现一起错、还能通过。

所以这条判据把一个 C 程序对着系统的真 glibc 编译，在两边跑同一组调用，并逐字节 比对标准输出，报出第一处不同的行。有两处归一化是有意为之，否则这个测试量的会是 实现细节而不是语义：标准只承诺 strcmp 的符号，所以符号和差都被检查； 而 glibc 的字符判定返回的是一个位掩码而不是 1，所以两边都在比对之前被归约成一个 是或否。

语言逼出来的东西

这项工作的规则是"libc 怎么实现，LibL 就怎么实现"。这门语言不是 C，所以有四处不得不不同、 有一处不得不新增。每一处都被写下来，而不是藏起来。

字符串字面量不带结尾符

于是对字面量调用 strlen 会读过结尾。在第一次探针里，它给空字符串返回了 17，一路读下去，直到碰巧遇上一个零字节。C 不需要为此写个函数，因为 C 里的 "abc" 本来就带着它的 NUL。这不是一处遗漏 —— 两种 str 类型不是同一个东西：这门语言的带着长度，C 的不带。LibL 加了 cstr_of 把一种转成另一种，而库里每一个 NUL 字符串函数都需要它。

没有变参函数

于是 snprintf 比 libc 的多取一个参数： snprintf(buf, cap, fmt, args, nargs)，其中 args 指向一个 64 位值的数组。转换说明符仍然决定每一个怎么读，和 libc 里一模一样。这是库里 唯一一处偏离的签名，而且它不纯粹是损失：libc 数不了自己的参数，给它太少就会 去读栈上碰巧有的东西；这里，太少意味着转换停下，而已经产出的部分被妥当地收尾。

没有函数指针

于是 qsort 的第四个参数是一个枚举，说明按什么比较，而不是一个比较函数。 那是一处真实的差异，而且它在某一个方向上不是降级：它把"这个排序按什么比较"从运行期的 一个地址挪进产物里的一个常量，于是不用读源码就能回答。代价随 它一起被说出来：不是内建几种之一的排序无法表达 —— 你自己写那个循环。

没有模块级可变全局

于是 strtok 变成 strtok_r，游标由调用方持着 —— POSIX 本来 就提供这个，所以这不是降级。一个藏着种子的 rand 也没法存在；这门语言用的 形状从调用方取状态，并且有意地不叫 rand。也没有 errno：strtol 饱和到边界值，然后正常返回，所以调用方改为 对着边界来比。

它不是什么

不是 libc 的替代品

LibL 是一个源码库，不是一个 C 目标文件能链接上去的归档。C 代码没法 调用它；那需要一条"从 Loment 到目标文件"的路，而那条路不存在。它替代的东西更窄，值得 说准确：一个 Loment 程序不得不手写 strcmp。

不是 libc 的全部

没有 malloc、calloc、realloc 或 free —— libc 的这几个依赖一个存在全局槽里的堆句柄，而语言没地方放它；这里 的库从调用方取它自己的 arena，而编译器自己的堆布局是私有的：从一个库伸手进去，会把 一处实现细节钉进库里。没有 FILE，没有 fopen 或 fread。进程或环境那一族里的一个都没有：exit、 abort、getenv。也没有浮点格式化，因为这门语言没有浮点类型。

没完工，也不假装完工

写它的过程暴露出周边系统里的缺陷 —— 其中有：一个辅助函数的重叠检查比的是偏移，而 libc 比的是地址；一个格式化器产出的 IR 被系统汇编器拒绝；一个依赖检查怪错了模块。这些都被 开成 issue，而不是顺手修掉，而这个库自己的判据有意地窄：它声称这些模块是合法单元，而 不声称它们的依赖也是。
