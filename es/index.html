Un lenguaje de programación de sistemas

Loment

Compila a ejecutables nativos x86-64 — ELF de Linux, PE de Windows, o un objeto autónomo para bare metal. Lo que entra en un artefacto es decisión del programa, y la compilación lo registra. El propio conjunto de herramientas está escrito en Loment.

Descargar Primeros pasos 

module hello fn _start() {    let s: str = "hello from Loment\n";    syscall4(1, 1, str_ptr(s) as u64, str_len(s) as u64);    syscall4(60, 0, 0, 0);}

$ loment run hello.lomt
hello from Loment

_start es el punto de entrada, porque un artefacto sealed no tiene runtime que llame a uno por ti. Tampoco hay printf — la salida pasa por la llamada al sistema write.

Un código fuente, dos clases de artefacto

Casi todos los ajustes de compilación viven fuera del lenguaje, donde quien lee el código fuente nunca los ve. Loment pone este dentro del programa — una línea, en la unidad raíz — y luego lo traslada al objeto de forma que la unidad exporta. Así, qué clase de artefacto se compiló es algo que puede responder incluso algo que no puede leer el código fuente en absoluto.

choose sealed

Qué es
El valor por defecto. Un artefacto sin puertos hacia el mundo.
Punto de entrada
fn _start()
Enlaza
Nada. Un símbolo no definido es un error, no una advertencia — así que un artefacto sealed no tiene, de forma demostrable, ni runtime ni libc.
Alcanza
Solo el código compilado dentro de él, más cualquier objeto que le entregues al enlazador y que ya sea autocontenido.

choose hosted

Qué es
La otra vía. Un artefacto declarado con permiso para alcanzar fuera de sí mismo.
Punto de entrada
fn main() -> u32
Enlaza
Bibliotecas reales. La compilación entrega el IR al conjunto de herramientas C del anfitrión en lugar del enlazador incluido.
Alcanza
libc, bibliotecas compartidas, y un runtime del anfitrión que incrustes. Los propios criterios del proyecto enlazan libstdc++ y libz e incrustan CPython.

Dónde está realmente la frontera. Alcanzar una biblioteca real implica pasar por el conjunto de herramientas del anfitrión tú mismo — tú nombras la biblioteca en la compilación. Una biblioteca C real todavía no es una dependencia instalable: el gestor de paquetes aún solo acepta bibliotecas de código fuente Loment. Esa parte se está construyendo.

Quién puede ejecutar qué, y en qué ámbito

Casi todos los lenguajes responden a ¿qué puede hacer este programa? Loment se organiza en torno a una pregunta más estrecha — quién puede ejecutar qué, en qué ámbito, y puede eso resolverse sin leer el código fuente? Tres cosas la sostienen. 

module native_cap capability blk_write : disk[0..4] revocable fn write(slot: u32) -> u32 {    guard blk_write(slot);    return slot;} fn literal_ok() -> u32 {    guard blk_write(2);    return 2;}

La línea 3 declara el rango que una unidad puede alcanzar. La línea 6 comprueba slot contra él en tiempo de ejecución, donde un índice fuera de rango aborta. La línea 11 es un literal, así que el compilador lo resuelve y no se emite nada.

Dominios de capacidad

Una unidad declara el rango que puede alcanzar, y una guard comprueba un índice contra él — en tiempo de compilación cuando el índice es un literal, y si no en tiempo de ejecución. La frontera se enuncia en lugar de disimularse: una guard acota el índice, no el sujeto, y no es una autorización.

Objetos de forma

Cada unidad exporta un resumen declarado y legible por máquina de lo que contiene y lo que alcanza, juzgado por dos validadores independientes — así "qué puede tocar esto" puede responderse sin leer el código fuente.

Una capa de compatibilidad

C, C++, Rust y Zig tras el C ABI; Go, Python, Java, JavaScript, Perl y Lua sobre un puente de procesos. En un artefacto sealed, lo que se enlaza debe ser autocontenido. choose hosted es la vía que alcanza bibliotecas reales, y los criterios la ejercitan contra libstdc++, libz y un CPython incrustado.

Qué más es distinto

Un modo de proyecto, no un atributo de crate

choose tiene cuatro dimensiones — qué capa puede usar el programa, cómo recupera memoria, si el artefacto puede llevar un runtime, y si puede alcanzar fuera de sí mismo. Cada una se escribe a lo sumo una vez, en la unidad raíz, y cada una pasa a ser una propiedad de todo el programa: un par contradictorio se rechaza, y el diagnóstico nombra el par y el motivo en lugar de decir "combinación ilegal".

Escrito en otras seis sintaxis

C, C++, Java, C#, Go o Python. Solo cambia la grafía; el significado es siempre el de Loment — es una sintaxis, no una semántica, y cada front end lo dice en su primera línea.

Una biblioteca que se importa módulo a módulo

La biblioteca estándar viene con el conjunto de herramientas y se alcanza como use vec, use map, use fs. Hay una importación de todo el paquete, pero arrastra todo a una sola unidad, y la documentación lo desaconseja.

Todo es personalizable

El sufijo del código fuente, la superficie de comandos, las bibliotecas — un directorio cuya identidad es un hash de contenido — y el propio conjunto de herramientas. No hay registro; los puntos de extensión son archivos en disco.

Qué no está terminado. El conjunto de herramientas es autoalojado en tiempo de ejecución — compila y se ejecuta sin Python y sin libc — pero el lado de desarrollo no lo es: la implementación de referencia y sus conjuntos de pruebas siguen en el repositorio, y el repositorio todavía no es "solo Loment". Las notas de la versión dicen en qué mitad está cada elemento pendiente.

Tres sistemas

Tres partes de Loment que son lo bastante grandes como para tener sus propios registros de diseño — y sus propias líneas de estado honestas.

LomentGC La recuperación como contrato por sitio: una escala de cuatro niveles, y cuánto es responsable el recolector, escrito en el artefacto. LVM — Loment VM Una segunda forma de ejecutar: un ejecutor adopta el artefacto cuando hace falta. El motor no existe, y la página lo dice primero. lompi Una biblioteca es un directorio de archivos Loment. Sin lenguaje de manifiesto, sin resolutor de versiones, y una identidad que es un hash de contenido.
