Loment VM

The VM is the next execution model the language is being readied for. Its first slice — a dimension and a gate — is being built. The engine does not exist.

There is no VM

No bytecode, no interpreter, no execution engine of any kind. That goes at the top rather than in a footnote, because a page about a plan is the easiest place for a reader to mistake the plan for the product.

What exists today is a specification and an implementation on a development branch: no part of it is on the main branch, in any release, or in any installed toolchain. The project says this about itself rather than letting you find out — it is the same debt runtime was in for a while, declared and carried in the artifact while doing nothing, before it was paid.

What the first slice specifies

Two things, both about permission rather than capability. Neither is a feature you can use.

A fifth dimension

choose had four dimensions — which layer the program may use, how it reclaims memory, whether the artifact may carry a runtime, and whether it may reach outside itself. vm would be the fifth, answering a different question: which execution model is this program for? Left unwritten it is no_vm, which is what everything was before the dimension existed.

A gate, not a feature

In a release build, choose vm would be a compile-time error; only the development channel would accept it. The rule the project set itself is blunt — until the first usable VM exists, every call to it is illegal in a release — so that an installed toolchain can never accept a promise it cannot keep.

Why the value would not be vm_t0 or similar. The same rule the runtime dimension follows: the value says whether, never which. What sits inside will change over the years, and a name that encoded today's tier would have to be renamed to add tomorrow's.

Why a gate at all

A dimension that compiles in a release and then does nothing is a lie with good formatting. Gating it means the word cannot appear somewhere it would mislead, and that the day the engine lands the gate opens rather than the promise being retrofitted.

A gate needs a notion the repository did not have — is this compiler a release build or a development one? The spec puts it in one constant, one value per side, flipped at packaging time. Keeping it to a single line is deliberate: the packaged language guide is copied into a distribution unmodified so that "the copy in the package is the copy in the repository" stays checkable, and one line is the smallest way to bend that rule. The cost is stated with it — the shipped compiler seed would no longer equal the repository's byte for byte, so the criterion drops from "identical" to "reproducibly equal, and the difference is exactly that one constant".

What it could become

The design record describes a ladder, in the same spirit as the reclamation one: an interpreter first, then feedback collected from real runs, then a baseline compiler, then an optimising compiler that can give a guess up when it turns out wrong. None of those steps is a feature today, and this page will not pretend otherwise.

When the engine arrives, the dimension is already the place a new execution model has to plug in — and the gate is already the thing that keeps it from being announced before it works.
