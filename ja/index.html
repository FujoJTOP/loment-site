システムプログラミング言語

Loment

ネイティブの x86-64 実行ファイル —— Linux ELF、Windows PE、あるいはベアメタル向けの freestanding オブジェクト —— にコンパイルする。その中に何が入るかはプログラム自身の 決定であり、ビルドがそれを記録する。ツールチェイン自体が Loment で書かれている。

ダウンロード はじめに 

module hello fn _start() {    let s: str = "hello from Loment\n";    syscall4(1, 1, str_ptr(s) as u64, str_len(s) as u64);    syscall4(60, 0, 0, 0);}

$ loment run hello.lomt
hello from Loment

_start がエントリポイントである。sealed な成果物には、代わりにエントリポイントを 呼んでくれる runtime がないからだ。printf もない —— 出力は write システムコールを通る。

ひとつのソース、二種類の成果物

多くのビルド設定は言語の外にあり、ソースを読む者には決して見えない。Loment はこの設定を プログラムの中に置く —— ルートユニットに一行 —— そしてそれを、ユニットがエクスポートする 形式オブジェクトへと持ち込む。だからどちらの種類の成果物がビルドされたかは、ソースを まったく読めないものにも答えられる。

choose sealed

これは何か
既定。外界へのポートを持たない成果物。
エントリポイント
fn _start()
リンク
なし。未定義シンボルは警告ではなくエラーである —— だから sealed な成果物には runtime も libc もないことが証明できる。
到達範囲
それにコンパイルされたコードだけ、加えてリンカに渡したオブジェクトのうち既に 自己完結しているもの。

choose hosted

これは何か
もう一方の道。自分自身の外に到達することが許されると宣言された成果物。
エントリポイント
fn main() -> u32
リンク
実在のライブラリ。ビルドは IR を、同梱のリンカではなくホストの C ツールチェインに 渡す。
到達範囲
libc、共有ライブラリ、そして自分で埋め込むホスト runtime。プロジェクト自身の判据は libstdc++ と libz をリンクし、CPython を埋め込む。

境界が実際どこにあるか。実在のライブラリに到達するとは、自分でホストの ツールチェインを通すということだ —— ビルドでそのライブラリを名指しする。実在の C ライブラリは まだインストール可能な依存ではない。パッケージマネージャが受け取るのは今も Loment の ソースライブラリだけである。その部分は作っている途中だ。

誰が、どの範囲で、何を実行できるか

多くの言語はこのプログラムは何ができるか?に答える。Loment はもっと狭い問いを軸に 組み立てられている —— 誰が、どの範囲で、何を実行でき、それをソースを読まずに 決着できるか?それを支えるのは三つだ。 

module native_cap capability blk_write : disk[0..4] revocable fn write(slot: u32) -> u32 {    guard blk_write(slot);    return slot;} fn literal_ok() -> u32 {    guard blk_write(2);    return 2;}

3 行目がユニットの到達しうる範囲を宣言する。6 行目は slot を実行時にそれと 照合し、範囲外の添字はトラップする。11 行目はリテラルなので、コンパイラが決着させ、 何も出力されない。

ケイパビリティドメイン

ユニットは到達しうる範囲を宣言し、guard が添字をそれと照合する —— 添字がリテラルならコンパイル時に、そうでなければ実行時に。境界はうやむやにせず 明示される。guard が区切るのは添字であって対象ではなく、またそれは認可ではない。

形式オブジェクト

すべてのユニットは、自分が何を含み何に到達するかの、宣言された機械可読な要約を エクスポートし、それは二つの独立した検証器が判定する —— だから「これは何に触れうるか」 はソースを読まずに答えられる。

互換レイヤー

C、C++、Rust、Zig は C ABI の背後で。Go、Python、Java、JavaScript、Perl、Lua は プロセスブリッジ越しに。sealed な成果物では、リンクされるものが自己完結していなければ ならない。choose hosted が実在のライブラリに到達する道であり、判据はそれを libstdc++、libz、埋め込んだ CPython に対して実際に走らせる。

ほかに何が違うか

crate 属性ではなくプロジェクトモード

choose は五つの次元を持つ —— プログラムが使ってよい層、メモリをどう 回収するか、成果物が runtime を積んでよいか、自分自身の外に到達してよいか、そして どの実行モデル向けか。それぞれは ルートユニットに多くとも一度だけ書かれ、それぞれがプログラム全体の性質になる。矛盾する 組は拒否され、その診断は「不正な組み合わせ」と言う代わりに、その組と理由を名指しする。

六つの別の構文でも書ける

C、C++、Java、C#、Go、Python。変わるのは綴りだけで、意味は常に Loment のものである —— それは構文であって意味論ではなく、各フロントエンドはそのことを自分の最初の行に 書いている。

モジュールを一つずつインポートするライブラリ

標準ライブラリはツールチェインに同梱され、use vec、use map、 use fs として届く。パッケージ全体のインポートもあるが、それはすべてを ひとつのユニットに引き込んでしまい、ドキュメントはそれを使わないよう勧めている。

すべてがカスタマイズ可能

ソースの拡張子、コマンドの面、ライブラリ —— その同一性が内容ハッシュであるディレクトリ —— そしてツールチェインそのもの。レジストリはない。拡張点はディスク上のファイルである。

まだ終わっていないこと。ツールチェインは実行時にはセルフホストである —— Python も libc もなしでコンパイルし実行する —— が、開発側はそうではない。参照実装とその テスト群は今もリポジトリにあり、リポジトリはまだ「Loment だけ」ではない。残っている項目が どちらの半分に属するかはリリースノートに書かれている。

システム

独自の設計記録を持つほど大きく、そして正直な現状の一行を持つ、Loment の各部分。

LomentGC 回収をサイトごとの契約として捉える。四段のはしごと、コレクタがどこまで責任を負うかが成果物に書き込まれる。 LVM — Loment VM もうひとつの実行のしかた —— 実行体が産物を必要に応じて取り込む。エンジンは存在せず、そのページはまずそう書いている。 lompi ライブラリとは Loment ファイルのディレクトリである。マニフェスト言語もバージョン解決器もなく、同一性は内容ハッシュ。 LibL 標準ライブラリの libc の面。名前も引数の順も C のままで、判定基準は Python ではなく実物の glibc と比べる。

もっと読むには

学習 効く順番と、各段に何が足りないか —— 並べて書いてある。 はじめに インストールして最初のプログラムを走らせる。ネイティブバイナリ。Python も clang も WSL も要らない。 サンプル 短いプログラム。それぞれが出力したものを添えて —— そしてそれらに含まれないものも。 さらに多くのサンプル リポジトリにある全部。そのすべてが今日リンクするわけではない。 リリース履歴 最初の Loment から、いま作っているものまで —— 各版が何のためのものだったか。 ロードマップ プロジェクトが目指している各版と、それぞれが何のためのものか —— 計画であって、約束ではない。 Wiki 言語、ツールチェイン、ロードマップを、ページごとに。 README 何のためにあるのか、ほかに何が違うのか、そして正直に言って何がまだ終わっていないのか。 Discord プロジェクトが話をする場所。質問はバグ報告と同じくらい歓迎される。
