A systems programming language

Loment

It compiles to native x86-64 executables — Linux ELF, Windows PE, or a freestanding object for bare metal. What goes into one is the program's decision, and the build records it. The toolchain is itself written in Loment.

Download Get started 

module hello fn _start() {    let s: str = "hello from Loment\n";    syscall4(1, 1, str_ptr(s) as u64, str_len(s) as u64);    syscall4(60, 0, 0, 0);}

$ loment run hello.lomt
hello from Loment

_start is the entry point, because a sealed artifact has no runtime to call one for you. There is no printf either — output goes through the write system call.

One source, two kinds of artifact

Most build settings live outside the language, where a reader of the source never sees them. Loment puts this one in the program — one line, in the root unit — and then carries it into the form object the unit exports. So which kind of artifact was built is answerable by something that cannot read the source at all.

choose sealed

What it is
The default. An artifact with no ports to the world.
Entry point
fn _start()
Links
Nothing. An undefined symbol is an error, not a warning — so a sealed artifact provably has no runtime and no libc.
Reaches
Only the code compiled into it, plus any object you hand the linker that is already self-contained.

choose hosted

What it is
The other path. An artifact declared allowed to reach outside itself.
Entry point
fn main() -> u32
Links
Real libraries. The build hands the IR to the host C toolchain instead of the bundled linker.
Reaches
libc, shared libraries, and a host runtime you embed. The project's own criteria link libstdc++ and libz and embed CPython.

Where the boundary actually sits. Reaching a real library means going through the host toolchain yourself — you name the library in the build. A real C library is not yet an installable dependency: the package manager still takes Loment source libraries only. That part is being built.

Who can run what, in what scope

Most languages answer what can this program do? Loment is arranged around a narrower question — who can run what, in what scope, and can that be settled without reading the source? Three things carry it. 

module native_cap capability blk_write : disk[0..4] revocable fn write(slot: u32) -> u32 {    guard blk_write(slot);    return slot;} fn literal_ok() -> u32 {    guard blk_write(2);    return 2;}

Line 3 declares the range a unit may reach. Line 6 checks slot against it at run time, where an out-of-range index traps. Line 11 is a literal, so the compiler settles it and nothing is emitted.

Capability domains

A unit declares the range it may reach, and a guard checks an index against it — at compile time when the index is a literal, otherwise at run time. The boundary is stated rather than glossed: a guard bounds the index, not the subject, and it is not authorisation.

Form objects

Every unit exports a declared, machine-readable summary of what it contains and what it reaches, judged by two independent validators — so "what can this touch" is answerable without reading the source.

A compat layer

C, C++, Rust and Zig behind the C ABI; Go, Python, Java, JavaScript, Perl and Lua over a process bridge. On a sealed artifact what links in must be self-contained. choose hosted is the path that reaches real libraries, and the criteria exercise it against libstdc++, libz and an embedded CPython.

What else is different

A project mode, not a crate attribute

choose has four dimensions — which layer the program may use, how it reclaims memory, whether the artifact may carry a runtime, and whether it may reach outside itself. Each is written at most once, in the root unit, and each becomes a property of the whole program: a contradictory pair is refused, and the diagnostic names the pair and the reason rather than saying "illegal combination".

Written in six other syntaxes

C, C++, Java, C#, Go or Python. Only the spelling changes; the meaning is always Loment's — it is a syntax, not a semantics, and each front end says so on its first line.

A library you import one module at a time

The standard library ships with the toolchain and is reached as use vec, use map, use fs. There is a package-wide import, but it pulls everything into one unit, and the documentation advises against it.

Everything is customizable

The source suffix, the command surface, the libraries — a directory whose identity is a content hash — and the toolchain itself. There is no registry; the extension points are files on disk.

What is not finished. The toolchain is self-hosted at run time — it compiles and runs with no Python and no libc — but the development side is not: the reference implementation and its test suites are still in the repository, and the repository is not yet "only Loment". The release notes say which half each remaining item is in.

Systems

Parts of Loment that are large enough to have their own design records — and their own honest status lines.

LomentGC Reclamation as a per-site contract: a four-level ladder, and how much the collector is responsible for written into the artifact. LVM — Loment VM A second way to run a program — an artifact an executor adopts on demand. The engine does not exist, and the page says so first. lompi A library is a directory of Loment files. No manifest language, no version solver, and an identity that is a content hash. LibL The standard library's libc face: C's names, C's argument order, and a criterion that compares against real glibc instead of against Python.
