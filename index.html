A systems programming language

Loment

Loment builds a native executable that stands on its own — no runtime, no libc, nothing underneath. What a program may reach is written in the source and recorded in the binary, so a build can check it without reading your code. The toolchain is itself written in Loment.

Download Get started 

module hello fn _start() {    let s: str = "hello from Loment\n";    syscall4(1, 1, str_ptr(s) as u64, str_len(s) as u64);    syscall4(60, 0, 0, 0);}

$ loment run hello.lomt
hello from Loment

This is the whole program. _start is where the machine begins, and the text goes out through the write system call — a program that links nothing has no printf underneath it to call. Nothing is done for you, and nothing is in the way.

Two kinds of program

Most languages decide in a build file what goes into the binary — a file the person reading the source never opens. Loment puts that decision inside the program: one line, in the file you start from, carried into a machine-readable summary the binary ships with. So "which kind of program is this?" is answerable without reading any code at all.

choose sealed

What it is
The default. A program with no openings to the outside.
Entry point
fn _start()
Links
Nothing. An undefined symbol is an error there, not a warning — which is what makes it provable that a sealed program carries no runtime and no libc.
Reaches
Only what was compiled into it, plus any object file you hand the linker that is already self-contained.

choose hosted

What it is
The other path. A program that is allowed to reach outside itself.
Entry point
fn main() -> u32
Links
Real libraries. The build hands its output to the host's C toolchain instead of using the linker that ships with Loment.
Reaches
libc, shared libraries, and a host runtime you embed. The project's own tests link libstdc++ and libz and embed CPython.

The boundary, exactly. Reaching a real library means going through the host toolchain yourself — you name the library in the build. A real C library is not yet an installable dependency: the package manager still takes Loment source libraries only. That part is being built.

What a program is allowed to touch

Most languages answer the question what can this program do? — and the answer is usually "whatever it wants". Loment is built around a narrower one: what is this program allowed to reach, and can that be settled without reading its source? Three things carry it, and the first one is visible in the code. 

module native_cap capability blk_write : disk[0..4] revocable fn write(slot: u32) -> u32 {    guard blk_write(slot);    return slot;} fn literal_ok() -> u32 {    guard blk_write(2);    return 2;}

Line 3 declares the range a unit may reach. Line 6 checks slot against it at run time, where an out-of-range index stops the program. Line 11 is a literal, so the compiler settles it ahead of time and emits nothing.

A range the code declares

A unit — one source file and what it imports — declares the range it may reach, and a guard checks each access against that range: at compile time when the index is a constant, at run time otherwise. Loment calls this a capability domain, and states the boundary rather than glossing it — a guard bounds the index, not the subject, and it is not authorisation.

A summary the binary carries

Every unit exports a machine-readable summary of what it contains and what it reaches, and two independent programs check it. So "what can this touch?" has an answer that does not require reading your code. The summary has a name: a form object.

Calling code from ten other languages

C, C++, Rust and Zig come in through the C ABI; Go, Python, Java, JavaScript, Perl and Lua through a process bridge. On a sealed program, whatever you link in has to be self-contained. choose hosted is the road to real libraries, and the project's tests drive it against libstdc++, libz and an embedded CPython.

What has already been built with it

A language this young is usually described by what it hopes to become. Here is what Loment is already doing — all of it in the repository, all of it downloadable.

The toolchain

The compiler, the linker, the formatter, the language server and the package manager all ship as Loment source, and they run with no Python underneath them. The compiler is the largest program written in the language.

A disk driver

ahci.lomt talks to a SATA disk: it reads the register block, counts the implemented ports, and issues commands. The register block is handed in by the caller, so the same code runs inside an operating system or on a hosted machine.

A terminal interface

lumtui draws text, boxes and layout to a terminal — a small library, written the way you would write yours.

The compiler is under loment/selfhost/, the libraries under loment/lib/, and the examples under loment/examples/.

What else is different

The whole program's settings, in one line

One line, in the file you start from, settles five things about the whole program: which layer of the library it may use, how it reclaims memory, whether it may carry a runtime, whether it may reach outside itself, and which execution model it is written for. Ask for two settings that contradict each other and the compiler refuses — naming both and saying why, rather than "illegal combination". The mechanism is called choose.

Written in six other syntaxes

C, C++, Java, C#, Go or Python. Only the spelling changes; the meaning is always Loment's — it is a syntax, not a semantics, and each front end says so on its first line.

A library you import one module at a time

The standard library ships with the toolchain, and you reach it one module at a time: use vec, use map, use fs. There is a package-wide import that pulls everything in at once, and the documentation advises against it.

Everything is customizable

The source suffix, the set of commands you can run, the libraries — a directory whose identity is a content hash — and the toolchain itself. There is no registry; the extension points are files on disk.

What is not finished. The toolchain compiles and runs without Python and without libc — but the development side is not there yet. The reference implementation and its test suites are still in the repository, and the repository is not yet "only Loment". The release notes say which half each remaining item is in.

Systems

Four parts of Loment large enough to have their own design records — each with its own honest status line, including the one whose engine does not exist yet.

LomentGC Memory is freed by one of four strategies, picked per place it happens — and how much is left to the collector is written into the binary. LVM — Loment VM A second way to run a program — a binary an executor adopts on demand. The engine does not exist, and the page says so first. lompi A library is a directory of Loment files. No manifest language, no version solver, and an identity that is a content hash. LibL The standard library in C's shape: C's names and C's argument order, checked against real glibc rather than against Python.
